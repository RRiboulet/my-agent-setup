# Extensions, Settings, and Orchestrator Design

## Cross-extension event bus and settlement gate

Cross-extension imports have one home per extension: `.pi/extensions/orchestrator/events.ts` owns the typed event bus (`orchestrator:run-started`, `orchestrator:runs-snapshot`, `orchestrator:run-settled`, `orchestrator:plan-settled`, `orchestrator:todo-changed`, `orchestrator:gate-decided`, `orchestrator:subagent-dispatch`) imported by `todos.ts`, `review.ts`, and `subagent/index.ts`, keeping the publisher independent of the bus and avoiding directories without entry points (which fail the manifest test for the 11 `.pi/extensions/` entry points).

The settlement gate (`.pi/extensions/orchestrator/`) records a verdict as a session `custom` entry at `agent_before_settle`, publishes `orchestrator:gate-decided`, and acts only when a trusted project commits `.pi/orchestrator.json` (see `orchestrator.example.json` beside the extension). This repository intentionally commits none, so its gate is report-only.

When configured:
- Settlement blocking checks (`block.openTodos`, `block.repeatedFailure`, or configured `verification.command`) return `continue: true` with evidence instead of letting the run settle; `block.loops` enables the mid-run tool-call loop breaker on `tool_call`.
- An unresolved settlement condition keeps blocking while its evidence is unchanged; a new edit, todo, or failure re-arms it.
- Settlement blocks spend from `attemptCap` (default `3`), while mid-run loop-breaker blocks spend from a separate `loopAttemptCap` (default `3`) so loop blocks never exhaust the settlement gate budget. `orchestrator_override` skips the next block without spending an attempt.
- The gate never returns `continue: false` and checks that cannot be evaluated fail open.
- Delegated workers (`PI_ORCHESTRATOR_ROLE=worker`) record `scope: child` and block nothing.
- `advisor` asks a configured stronger model for a second opinion when a branch hits an unanswered loop block or repeated settlement failure, within a cooldown and per-branch budget (resolving credentials via `.pi/extensions/orchestrator/credentials.ts`). It injects the verdict as a `before_agent_start` prompt section (never replacing the system prompt or switching models, preserving the cached prefix), refuses loudly without credentials, and redacts secrets while excluding tool output bodies from its 4 KB digest.
- `workspace.lockScope` (`"worktree"` default or `"repo"`) sets the namespace for `orchestrator_reserve` file locks.

## Tiered wave orchestration (`/orchestrate` and `orchestrator_wave`)

- `/orchestrate <folder>` starts a wave in non-worker parent sessions: resolves `<folder>` against `cwd`, loads the dispatch ladder via `readLadder()`, rejects ticket graphs with cycles or dangling blockers (`blockingIssues(graph)`), soft-checks `ctx.model` against the ladder's highest tier, records an `orchestrator-wave` custom entry, and sends the kickoff turn. `/orchestrate status` (or `/orchestrate` while active) reports the wave state and live disk frontier; `/orchestrate abort` aborts an active wave.
- The parent/orchestrator always stays on the harness's current session model (`ctx.model`). The ladder pins only delegated roles; `wave-ladder.json` defaults `reviewer` to frontier inheritance (`inheritModel: true`, `thinking: "high"`) unless overridden by local ladder config, and wave dispatch plans/instructions propagate canonical `role` tags.
- `orchestrator_wave` (`exposure: "codemode"` when `codemode` or `tool_search` is active) drives the pure state machine (`pending -> triaged -> implementing -> reviewing (throughTier) -> verifying -> ready_to_commit -> done | blocked`), syncs ticket frontmatter via `setTicketStatus`, and verifies commit SHAs with `git rev-parse --verify` on `record_commit`.
- Ladder overrides resolve in order: `PI_ORCHESTRATE_LADDER`, `<PI_CODING_AGENT_DIR>/orchestrate-ladder.json`, then the bundled `wave-ladder.json` (falling back to `DEFAULT_LADDER`).
- Enforcement & gate coordination: while a wave is active, `tool_call` blocks `git commit` unless at least one ticket is `ready_to_commit`, and `agent_before_settle` blocks premature settlement (`block.wave`, default `true`) even without `.pi/orchestrator.json`—parking when delegated subagent runs are live and clearing once the wave completes or aborts. Active wave tickets in `ready_to_commit` satisfy `evaluateCompletionGate` so verified wave commits are never double-blocked, and wave `reviewer` subagent completions transition `reviewVerified` via `orchestrator:run-settled`.

## Isolated `/review` subagent dispatch (`.pi/extensions/review.ts`)

- `/review` keeps its interactive target picker (`pr`, `branch`, `commit`, `uncommitted`, `folder`), `REVIEW_GUIDELINES.md` lookup, and rubric prompt assembly, then dispatches an isolated `subagent` with `role: "reviewer"` and read-only tools (`["read", "grep", "find", "ls", "bash"]`) via `orchestrator:subagent-dispatch` (no inline parent `sendUserMessage` or parent-inline fixing loop).
- Settlement flows through `orchestrator:run-settled`, marking `reviewVerified` automatically when the dispatched `reviewer` completes after the last edit.

## Pragmatic Orchestrator delegation (`delegation.ts` / `delegation-runtime.ts`)

Enforced by default in parent sessions to keep exploration, multi-file edits, builds, and reviews in dedicated subagents while keeping small fixes cheap:

- **Modes, config, and bypasses**: `mode` is `"enforce"` (default), `"warn"`, or `"off"`. Configuration layers built-in defaults → global `~/.pi/agent/orchestrator-delegation.json` (or `$PI_CODING_AGENT_DIR/orchestrator-delegation.json` / `PI_ORCHESTRATOR_DELEGATION_CONFIG`) → trusted project `.pi/orchestrator.json` (`"delegation"` section; ignored when untrusted) → `PI_ORCHESTRATOR_DELEGATION` env override. `/delegation [enforce|warn|off|--json]` inspects or toggles the mode for the session, and a leading `!direct` (configurable `directPrefix`, case-insensitive) bypasses parent guardrails for that turn. When `mode !== "off"`, `before_agent_start` injects `sections.delegation` without replacing `systemPrompt` (including the repo-level skill delegation override noting that adapted skills' inline edit/test steps route through `subagent({ role: "coder" })` or `/orchestrate` in `enforce` mode).
- **Turn classification & discovery budgets**: user prompts are classified into `security` (2), `implement` (4), `quick-fix` (4), `debug` (5), `review` (5), or `qa` (8) discovery calls (`read`, `grep`, `find`, `ls`), reset per user prompt (`before_agent_start`). Exceeding the budget blocks (or warns in `warn` mode) and directs discovery to `subagent({ role: "explore", ... })`.
- **Parent edit caps, read-only `bash`, and steer-to-unlock**: direct `write` is denied on the parent; direct `edit` is allowed only on already-read files, at most 1 file per turn (`maxEditedFilesPerTurn: 1`), and at most `maxEditLines: 20` changed lines (trimming shared leading/trailing context lines). Parent `bash`/`powershell` is restricted to a strict read-only pipeline allowlist (`ls`, `wc`, read-only `git status|diff|log|show|rev-parse|branch|merge-base|describe|fetch` without `--force`/`--prune`/refspec colons/mutating flags/`--output`/`--ext-diff`/`-c`, and read-only `gh auth status|pr view|list|checks|diff|status|run list|view|issue list|view|release list|view` without `-t`/`--show-token`, piped only to `head|tail|wc|cat`, rejecting redirections, subshells, `;`, `&&`, `||`, or newlines). Issuing 2 steers (`subagent_interrupt`, `subagent_resume`, or delivered `subagent_answer`, tracked across `runStarted`/`runsSnapshot`/`resumeOf` lineage and ignoring unrecognized run IDs) for the same root run id unlocks direct parent editing for the remainder of that turn.
- **Post-edit verification, live-worker coordination, & thresholded `reviewer` gate**: non-doc edits (`.md`, `.txt`, `.rst`, `.adoc` exempt) from the parent or from child `activitySummary` (`editedFiles`, `passedCommands`, per-file `lastEditAt` on `orchestrator:run-settled`) arm a post-edit `tests` gate; reaching `>= 2` review-relevant files (`reviewThresholdFiles`) or `>= 50` changed lines (`reviewThresholdLines`) also arms a `code-review` gate. Both must clear (passing test command after the last code edit, ignoring weak/excluded commands; either a main-model review recorded via `orchestrator_record_review` with verdict `"pass"` or `"accepted_with_notes"` after post-edit `read` or read-only diff inspection `git diff`/`git show`/`git status`/`git log`/`gh pr diff`, or a completed `reviewer` / `security-reviewer` subagent or `/review` started at or after the last review-relevant edit, or active wave `ready_to_commit`) before `git commit`, `git push`, `gh pr create`, `gh pr merge`, or settlement (`agent_before_settle`, up to `settleAttemptCap: 2` per turn or one-shot `orchestrator_override`). Any subsequent review-eligible edit after `reviewVerified` was set resets `reviewVerified` unconditionally, even when that follow-up edit is below the initial file/line threshold. When live delegated runs exist at `agent_before_settle`: if `block.waitForSubagents: true` (or an active wave) is configured, the settlement gate parks cleanly without spending an attempt and wakes the parent (`orchestrator-resume`) when the last live run settles; otherwise (`waitForSubagents: false`, the default without `.pi/orchestrator.json`), `enforce` mode blocks settlement (up to `settleAttemptCap`, overridable via `orchestrator_override`) with `subagent_wait`/`subagent_status` guidance naming the live run IDs, and `warn` / `!direct` warn via `ctx.ui.notify` so active workers are never dropped silently. Aborted/non-completed settlements never block or wake. A successful `git commit` clears dirty state.
- **Nested `codemode` parity**: nested tool calls dispatched by `codemode` scripts with `parentToolCallId` set traverse the exact same `tool_call` and `tool_result` delegation hooks as top-level calls (`read` `viewedFiles` tracking, post-edit review inspection tracking via `read` / read-only diff commands, shared discovery budgets, write/edit caps, read-only `bash` allowlist, commit/PR gates, `subagent` role/fork gating and patching, and steer-unlock accounting), and both `orchestrator_override` and `orchestrator_record_review` keep `exposure: "codemode"` when `codemode` or `tool_search` is active.
- **Inert for worker children**: when `PI_ORCHESTRATOR_ROLE=worker` (`isDelegatedWorker === true`), no prompt section is injected, no guardrails or gates run, and `/delegation` is not registered.

## Settings and codemode policy

- `.pi/settings.json` (tracked in git) configures project defaults: `defaultTools: ["+tool_search", "+codemode"]` and `codemode.mode: "on"`.
- `.devcontainer/pi/settings.json` carries the enabled-model set and the same `defaultTools` / `codemode` settings, with no `packages` entry. It deliberately omits `defaultProvider` / `defaultModel`, leaving provider/model selection to the harness's current session.
- Prefer `codemode` to batch independent/parallel tool calls and filter large output before it hits context; use direct tools (`read`, `edit`, `write`, `bash`) for single-step edits or commands.

## Package installation and container isolation

- On a host working in this checkout, install by local path (`pi install /path/to/my-agent-setup`), never `git:github.com/RRiboulet/my-agent-setup`: project discovery and a git package both load `.pi/extensions`, causing duplicate tool registration errors.
- This repository's devcontainer uses a dedicated `PI_CODING_AGENT_DIR` on a private volume with no installed packages (`README.md` section "One copy of the extensions, never two").
- Other project devcontainers bake this repo at a pinned tag under `/opt/pi-packages/my-agent-setup` and point container settings there (tracked via `.devcontainer/pi-agent-setup.version`, Dockerfile `PI_AGENT_SETUP_TAG`, image label `org.my-agent-setup.pi-package`, and `/opt/pi-packages/my-agent-setup/.pi-agent-setup-tag`).

For pi's API contract, consult `/usr/lib/node_modules/@earendil-works/pi-coding-agent/docs/`; never modify pi itself.
